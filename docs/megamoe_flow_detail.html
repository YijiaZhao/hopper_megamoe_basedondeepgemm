MegaMoE 详细流程（SM90 / H20，EP8）

nsys 实测核实 整层 MoE = 2 个 kernel（l1_impl + l2_impl），5 类 warp 角色，3 组 mbarrier，2 处 NVLink scatter。
dispatch warp TMA producer decode warp math WG (WGMMA) epilogue NVLink scatter mbarrier

0. 实测基线（nsys，单卡 H4096/I640/E128，M=8）

kernel 符号instancesavg承载的工作
sm90_mxfp4_mega_moe_l1_impl8（=4 调用 × 2 半 grid）112.9 usdispatch + GG1 + SwiGLU + requant
sm90_mxfp4_mega_moe_l2_impl873.3 usGG2 + scatter + combine
整层只有这 2 个 kernel 符号，profile 里没有第三个（host 侧 launch_with_phase 也只有两次 launch）。 L1 : L2 ≈ 1.55 : 1 —— GG1 的 FLOP 是 GG2 的 2×（N=2I vs K=I），但 L1 还背 dispatch、L2 还背 scatter+combine，所以没到 2:1。

0.5 输入 / 输出：MegaMoE 的边界在哪

0.5.1 什么在 kernel 外，什么在里面

router 不在 MegaMoE 里。gate 线性层、softmax+topk、以及输入激活的量化，全部由框架侧（PyTorch 或独立 kernel）完成； MegaMoE 只接管「已知每个 token 去哪些 expert、激活已量化」之后的全部工作。

两个容易踩的坑：
· 内核注释里的「weight/act TMA is byte-identical to MXFP4/FP8」指的是搬运布局字节级一致（所以能复用同一条 swapAB-RF 流水）， 不是说数值是同一份 —— int 路的激活是真 int8。
· perf bench 对两条路都用 per_token_cast_to_fp8，因为测速只看指令数与布局、不看数值； 真正区分格式的是 tests/test_int4_mega_moe_correctness.py 里的 per_token_int8()。 拿 perf bench 的输出做数值判断会得到错误结论。
· 「a_int8」指的是中间激活（L2 的输入）与 L1 的 int8 激活，不要和权重的 int4 混淆。
为什么数据输入不是独立参数、而全塞在 sym_buffer 里： 因为激活、SF、路由信息都要被其它卡远程访问（scatter 写索引、pull 拉数据）， 必须放在对称内存（8 张卡同一虚拟地址各有一份）上，sym_buffer.map(ptr, rank) 才能直接寻址远端。 所以调用前要先 buffer.x.copy_(x_fp8) 这样填进去。

0.5.4 权重侧量化：w_int4_a_int8（QoQ）的真实构造

以下全部依据 tests/debug_int_largem.py :: quantize_qoq() 的实际代码（ZP=True 分支）， 非示意。我们的 int4 就是 QoQ，没有第二种 int4。 

def quantize_qoq(weight, group=128):
    w = weight.float()
    # ── Level 1：per-row s1（每个输出通道一行）
    s1 = (w.abs().amax(dim=-1) / 120.0).clamp_min(1e-30)
    s1 = s1.to(torch.bfloat16).to(torch.float32)   # 按 bf16 取整，保证内核 masked read 精确
    w8 = (w / s1).round().clamp(-112, 112)          # ZP 路：±112（非 ZP 路 ±120）

    # ── Level 2：per-group(128) 非对称 → uint4 + zero point，整数 s2
    w8g = w8.view(E, N, K // group, group)
    mn, mx = w8g.amin(-1), w8g.amax(-1)
    s2 = ((mx - mn) / 15.0).ceil().clamp(1, 127)      # 整数
    z  = (-mn / s2).round().clamp(0, 15)                # uint4
    w4 = (w8g / s2 + z).round().clamp(0, 15)             # uint4 权重

    dec8 = (w4 - z) * s2          # → int8，assert |dec8| ≤ 127
    dequant = dec8 * s1           # → 还原到 fp32

三个量的确切定义

量类型 / 范围粒度怎么算出来内核在哪一步用
s1fp32（按 bf16 取整）per-row（每个输出通道一行，amax(dim=-1)）amax / 120.0promote（fp32 域）
s2整数，[1, 127]per-group = K128ceil((max−min) / 15)promote（SHIFTXOR）
其它变体折进 LUT
zuint4，[0, 15]per-group = K128round(−min / s2)解码时逐字节减
两个必须讲准的数（客户会问）：
· s1 除的是 120，不是 127，且 ZP 路 w8 钳在 ±112。原因写在代码注释里： 要保证 s2 折叠后不溢出 int8 —— 7 · ceil(120/7) ≤ 126；ZP 路进一步留余量到 112。
· s1 是 per-row（每个输出通道），不是 per-tensor 也不是 per-K-group； 只有 s2 和 z 是 per-K128 组的。

s1 / s2 / z 怎么存：打包进一个 32-bit「plane」字

plane = (s1_bits & 0xFFFF0000)          # 高 16 位：s1 的 bf16 位型（低 16 位被掩掉）
      | (b1 << 8)                       # 中间字节：见下
      | s2                                # 低字节：整数 s2（1..127）
解码变体plane 中间字节 b1 存什么解码热路径
SHIFTXOR（当前推荐）原始 z纯 shift/mask + vsub4 逐字节减 z；s2、s1 都延到 promote
PRELUT原始 z用 [s2][z] 查预存的 smem LUT（要求 s2 ≤ 31）
算术 LUT（早期）nz = (−z·s2) mod 256把偏移折进 LUT 项，运行时构建
为什么 SHIFTXOR 能「不折 s2」还更快：s2 的组宽（128）正好等于 inline 档的 K128 promote 段， 所以 s2 可以和 s1 一样延到 fp32 promote 时一次乘完 —— 省掉每次解码构建带 s2 的 LUT。 这也是 w_int4_a_int8 每 K128 只 promote 一次（而 mxfp4 因 e8m0 组宽 32 要四次）的根本原因。
实验开关 DG_W4A8_INT_ZSUB_XOR=1 进一步把 vsub4 换成 (w + (128−z)) ^ 0x80（uint8 域不借位 + 一条 XOR 翻回 int8），SASS 算术指令 13 → 8。

2. Shared memory 布局与 mbarrier 分组

N_STAGES 是性能瓶颈所在：smem 被 dispatch ring + coeff + SFA/SFB + decode 缓冲挤占后， 权重 prefetch 只剩 3~4 级（理想需 8 级）→ latency-bound，DRAM 只到 26% roofline。 这就是「融合内核单 GEMM 比 FlashInfer 慢」的根因：FlashInfer 去融合，GEMM 独占 smem 做深 prefetch。

3. KERNEL 1 (l1_impl) —— 逐角色展开

3.1 dispatch warp：counting sort → scatter（送索引）→ pull（拉数据）

# ① 数：本 SM 每个 expert 收到几个 (token,topk) 对
for (tok, k) in my_tokens × topk:
    e = topk_idx[tok][k]
    atomicAdd_block(smem_cnt[e], 1)

# ② 抢：全局原子加，拿到本 SM 在每个 expert 里的连续区间起点
#    高 32 位计 SM 数、低 32 位计 token 数，一次原子加同时更新两者
for e in experts:
    send_value  = (1 << 32) | smem_cnt[e]
    smem_cnt[e] = atomic_add(global_expert_send_count[e], send_value)   # 返回旧值=我的起点

# ③ 散：算出目标卡 + 槽位，NVLink 直写 —— 排布与通信合一
for (tok, k) in my_tokens × topk:
    e        = topk_idx[tok][k]
    dst_rank = e // E_per_rank                      # 该 expert 在哪张卡
    slot     = atomicAdd_block(smem_cnt[e], 1)      # 在该 expert 内排第几个
    *sym_buffer.map(dst_ptr, dst_rank) = token_topk_idx      # ★ scatter

# ④ 拉（pull）：方向与 ③ 相反 —— 把散落在各卡、路由到「我负责的 expert」的 token 搬过来
for token_slot in my_share:
    # ③ 阶段各卡只写了索引，这里先解出它是谁
    src = workspace.get_src_token_topk_idx(expert, src_rank, token_idx_in_rank)
    src_token_idx = src // topk        # 哪个 token
    src_topk_idx  = src %  topk        # 它的第几个 expert 选择

    # ①激活数据：TMA 1D 从远端拉 kHidden 字节（fp8/int8）
    ptx::tma_load_1d(pull_buffer,
                     sym_buffer.map(input_token[src_token_idx], src_rank),
                     pull_mbarrier, kHidden)

    # ②激活 SF：per-128 K 一个 float（H=4096 → 32 个），逐 lane 线性写入本地 SF pool
    for j in range(kHidden // 128):
        local_sf[j * kSFRingStrideTokens + sf_pool_token_idx] = remote_sf[j]

    # ③routing weight：留到最后 COMBINE 加权用，提前搬来省一次远程读
    weight = *sym_buffer.map(input_topk_weights + src, src_rank)
    l1_topk_weights[pool_token_idx] = weight

    mbarrier_arrive_and_set_tx(pull_mbarrier, kHidden)
    mbarrier_wait_and_flip_phase(pull_mbarrier, phase)

# 落地位置：pool_token_idx = expert_pool_block_offset * BLOCK_M + token_idx_in_expert
#   ⇒ 同一 expert 的 token 在本地连续，GEMM 直接当稠密矩阵算，无需 gather
pull 搬的三样每 token 大小搬运方式用途
① token 激活数据kHidden 字节（fp8/int8，H=4096）TMA 1D tma_load_1d喂给 GG1 当 A 矩阵
② 激活 SFkHidden/128 个 float（=32）逐 lane 拷贝GG1 的 per-token × K128 scale
③ topk_weight1 个 float单线程读L1 epilogue 先乘进 amax；
最后 COMBINE 做 Σ wk·resultk
scatter 与 pull 方向相反，别搞混：
· scatter（③）：我卡上的 token → 写到「拥有该 expert 的那张卡」，写的只是索引；
· pull（④）：我卡负责的 expert → 按这些索引，把真正的数据从各远端卡拉过来。
两步合起来才完成一次 all-to-all 语义的 dispatch，但全程是单向远程访问、无集合汇合点。
为什么不需要独立 permute kernel：槽位由原子加当场算出，token 直接写到「目标卡 + 该 expert 区间内的位置」， 落地即按 expert 连续排好；SF 用简单线性映射同步排好（无需 4×32 转置）。

3.2 TMA producer + decode：多级流水的前两级

# TMA warp（B = 权重）
for k_blk in K_blocks:
    empty_barriers[stage].wait(phase)          # 等 math WG 腾出这一级
    cp.async.bulk.tensor(W_gmem[k_blk] → smem_b[stage],
                         mbar=full_barriers[stage])  # 到齐字节数自动 arrive（expect_tx）
    advance(stage)                                # index+1，绕环则 phase 翻转

# decode warp（4bit → 8bit，就地在 smem）
for k_blk in K_blocks:
    full_barriers[stage].wait(phase)
    # w_int4_a_int8 ：t = prmt(uq); w = (t|t<<4)&0x0F0F0F0F; d = vsub4(w, z)
    #           新变体 ZSUB_XOR： d = (w + (0x80808080-z)) ^ 0x80808080  （省 vsub4）
    # mxfp4  ：lut = exp_offset*0x08080808 + base;  d = prmt(lut_hi, lut_lo, code&0x7777)
    smem_b[stage] = decode(smem_b[stage], coeff)
    dequant_barriers[stage].arrive()

3.3 math warpgroup：WGMMA + promote + epilogue

for (expert, m_blk, n_blk) in my_tiles:
    final_acc = 0
    # ---------- mainloop：一段 = BLOCK_K = 128 ----------
    for k_blk in K_blocks:
        dequant_barriers[stage].wait(phase)
        wgmma.fence()
        for j in range(4):                       # 4 条 K32 WGMMA
            wgmma.mma_async(acc, smem_a[stage], smem_b[stage][j])   # 异步，发了就走
        wgmma.commit_group();  wgmma.wait_group(0)  # 读 acc 前必须 wait
        empty_barriers[stage].arrive()            # 还给 TMA

        # ★★ promote：三种格式性能差异的唯一来源 ★★
        #   w_int4_a_int8      : 每 K128 一次（s2 组宽=128，天然对齐 BLOCK_K）
        #   mxfp4        : 每 K32 四次（e8m0 组宽=32）→ 比 int4 慢 ~13%
        #   scaled-MXFP4 : 每 K128 一次（scale 已折进 decode 的 LUT）→ 反超 int4
        final_acc += promote(acc, scale)
        advance(stage)

    # ---------- L1 epilogue：SwiGLU + per-token 量化 ----------
    for p in pairs:                                # gate/up 交错布局（granularity-8）
        y[p] = silu(clamp(gate[p])) * clamp(up[p])
        amax_r0 = max(amax_r0, |y[p]|)              # 每行（=每 token）各自累
    amax_r0 *= |topk_weight|
    amax_r0 = warp_reduce<4>(amax_r0, Max)         # ★ 只跨 4 lane，不跨 CTA

    sf_inv = 127.0 / amax_r0                        # int8；fp8 e4m3 则用 448
    q      = quantize(y, sf_inv)                    # int8 借 fp8 buffer 搬运 → 避开 NaN 位型
    TMA_store(q → L1_out)
    write_float(sf → L2_acts_SF_buf)                # per-token × per-K64
warp_reduce<4> 这一行是免掉 reduce kernel 的关键： L2 激活 SF 的分组宽度（K64）特意等于一个 L1 N-block 的输出宽度， 所以 per-token amax 的规约完全在 block 内（寄存器 + 4 lane shuffle）完成。 若改成「全局 per-token」scale，一个 token 的行横跨所有 N block → 必须跨 CTA 规约 → 得单独插 reduce kernel（CuTeDSL 那条路的困境）。

    dst_rank = orig_rank_of(row)
    *sym_buffer.map(combine_buf_ptr, dst_rank) = bf16_row   # ★ scatter 回原卡

# ---------- COMBINE：top-k 规约 ----------
grid_barrier()                                      # 等所有卡的 scatter 落地
for tok in my_tokens:
    out[tok] = Σ_k  topk_weight[tok][k] * combine_buf[tok][k]    # BF16 加权求和

5. 流水时序 —— 计算与通信如何逐 tile 错开

5.1 tile 级：通信是「算完一个 tile 发一波」，不是背景常驻

本图的放大倍数：横轴是 tile 序号，一个 GEMM tN 方框 = 一整个 tile 的计算， 内部的 TMA 取权重 / decode / WGMMA 全被折叠进这个方框 —— 那一层展开见 5.3。
本图只画 跨卡的两处数据流（dispatch pull 与 scatter），因为第 5 节的主题是计算与通信重叠； 权重加载是卡内行为（权重在 EP 下不跨卡，每张卡永久持有自己 expert 的权重），故不在本图出现。
头尾藏不掉：第一个 tile 的 pull（prologue）没有前序计算可盖；最后的 grid barrier + COMBINE 必须等所有卡 scatter 落地。 M 越小 tile 越少 → 头尾占比越大 → 重叠窗口越短。这解释了为什么小 M 时相对 FlashInfer 的优势更小（m32 仅 +2%，m64 达 +15%）。

5.2 对比：为什么 FlashInfer 藏不掉

差别的本质不是「谁通信快」，是「能不能错拍」。 allreduce 是集合原语，要求所有 rank 到齐才能进行，天然是同步点，只能排在 GEMM 之后； scatter 是单向逐 tile 的远程写，发出即返回、没有汇合点，所以能与后续 tile 的计算重叠。 这 28~36 us 的差，就是 EP8 下 MegaMoE 赢 FlashInfer 的全部来源。

5.3 CTA 内部：三级 mbarrier 流水 —— 放大 5.1 里的一个 GEMM tN 方框

dispatch warp 为什么是虚线：本图横轴是一个 tile 内部的 K-block 迭代， 而 dispatch warp 不参与这个循环 —— K 循环用 full/dequant/empty 三组 barrier， dispatch 用的是另一组 dispatch_barriers，两者只通过 l1_full_count 计数器间接握手 （GEMM 自旋等某个 pool block 填满才开算）。它的工作量也是有限的： 数 expert → 抢 offset → scatter 索引 → 拉完自己那份 token → cleanup_workspace，干完即收工， 通常早于 GEMM 结束。tile 之间的真实错拍见 5.1。

这是 ExCP 结构（专职 decode warp）。LiquidGEMM（arXiv 2509.01229）实测该结构在小 batch 是负收益 —— RF↔SMEM 往返 + 显式同步的开销盖过重叠收益；其 ImFP 方案改为 每个 Compute WG 自解码自 MMA、不回写 SMEM。我们客户形状 m=4~64 全在小 batch 区，这是待验证的优化方向。

为什么用 scatter 而不是 all-to-all / allreduce：scatter 是逐 token 的细粒度远程写，不是集合原语， 不需要全卡同步，因此可以由专职 warp 发出并与 WGMMA 重叠。集合原语必须等全体到齐，藏不掉。
这正是 EP8 下 MegaMoE 能赢 FlashInfer 的原因：对手要在 GEMM 之后串行做 2 次 allreduce（实测 28~36 us），我们把它藏进了计算。
