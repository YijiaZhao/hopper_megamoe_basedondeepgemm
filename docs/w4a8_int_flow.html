分段文字说明

〇、离线准备：权重的两级量化（每个专家、每层各做一次，存盘）

原始权重（bf16）→ 第一级：每个输出通道（每一行）求最大绝对值，得到行缩放 s1（bf16，一行一个），把整行除以 s1 量化到 8 位整数（限制在 ±112，为下一步留余量）→ 第二级：每 128 个 K 元素为一组，非对称量化到 4 位无符号整数——每组求最小/最大值，得到整数组缩放 s2（1 字节整数）和零点 z（4 位），使得 8 位值 ≈ (4位值 − z) × s2
重建值 (w4−z)×s2 按构造不超过 ±127，永远装得进 8 位整数——这是后面"整数域折叠"合法的前提。
落盘三样东西：① 4 位打包权重（每字节两个权重，长驻显存）② 元数据字（每行每 128 个 K 一个 32 位字：低字节放 s2、次字节放 z、高 16 位放 s1 的 bf16 位模式）③ 布局按 kernel 需要重排（gate/up 交织、tile 优先）

一、激活怎么进来（每次前向、动态量化）

token 激活 x（bf16，来自上一算子）→ 每个 token 独立求整行最大绝对值 ÷127 得到token 缩放（每 token 一个浮点数）→ 量化成 8 位整数→ 整数字节 + 缩放一起经通信缓冲区，按路由结果分发到各专家所在的卡（跨卡流量也因此减半）
缩放不是 per-tensor：token 之间幅度差可达一个数量级，必须每 token 自适应。

二、分两段跑：按 token 数自动选实现（唯一开关：1024）

二A、token 数 ≤ 1024：swapAB 路径（权重 4 位直进 kernel，寄存器里查表解码）

循环沿 K 方向推进，每次处理 128 个 K（一个流水段）：
TMA 搬运引擎→ 4 位打包权重 + 元数据字 + 激活整数字节，装进共享内存（4~8 级流水（按档位自动选），边算边搬）
① 数学 warp 读本行元数据字：取出 s2、z、s1→ ② 取解码表（v3 起为预存表）：表 = { (0−z)×s2, (1−z)×s2, …, (7−z)×s2 }。关键观察：(s2, z) 的组合总共只有 18×16=288 种 → 全部 288 行乘积表在编译期就算好、写死在程序体里，kernel 启动时一次性搬进共享内存（2.3KB），解码时按本组的 (s2,z) 直接取 8 字节一行——建表指令归零（此优化 flash M1 −23%）。早期的"现场建表"（两条 32 位乘法批量生成表项，合并零点必须按字节加、普通加法会跨字节进位——踩过的坑）保留为对称格式（无零点）路径，因其本来就只要 2 条指令
③ 查表解码：每个权重取 4 位中的低 3 位当索引，一条 byte_perm 指令同时查 4 个权重，直接吐出"乘好 s2、减好 z"的 8 位整数；高位半区（原值 ≥8 的）再统一按字节加上 8×s2。产物留在寄存器，用完即弃，不占长期空间→ ④ tensor core：WGMMA 指令（固定形状 m64×n×k32，8 位输入的 k 永远是 32），权重当 A 从寄存器喂、token 当 B（这就是 swapAB：token 少时换个方向填满 64 行的硬件格子），4 条指令首尾相接累进同一个 32 位整数累加器（同一把尺子才能同账累加——s2 已折光，所以合法）
⑤ promote（补缩放）：4 条指令全部落定后，把整数累加器转成浮点，乘上「该 token 的缩放 × 该行的 s1」（两个缩放沿不同轴变化，只能在输出网格上逐元素补），累进最终浮点累加器。每 128 个 K 才做一次，且实测不在关键路径上（同一 SM 上邻居 warp 的搬运和矩阵乘自然把它盖住），所以不必额外买重叠
解码的 ALU 全部发生在上一批 WGMMA 的异步空窗里（发射完矩阵乘指令后 tensor core 自己转几百拍，CUDA core 正好去解下一批的码）——tensor core 和 CUDA core 是两种独立硬件，流水并行。
v3 判定：每个 SM 住几个 CTA？（运行时自动门控）
① pro M1~8 / flash M2~8 → 2 个 CTA：小 token 时流水线是"延迟受限"而非带宽受限（证据：4 位权重读量只有 FP8 的一半却只能打平→带宽没用满）。把流水线 8 段瘦身到 4 段、寄存器按角色配给，两个 CTA 共驻一个 SM，两条独立流水线互相填掉对方等搬运/等唤醒的空转（SM 级预取总量不变，2×4=8 段）。实测 pro M8 −12%、flash M8 −15%。
② flash M1 → 1 个 CTA：该点协议开销主导（活跃 expert 极少、没有数学气泡可填），双 CTA 只是给 grid 同步加倍到达数，实测 +43%——门控明确禁用。
③ M≥16 及预解码路径 → 1 个 CTA：流水线已被吞吐喂饱，气泡自然消失；此时要的是 8 段深预取，双 CTA 反而砍浅缓冲。路径与 v2 逐位一致。

二B、token 数 ≥ 1280：预解码路径（先整层解好码，GEMM 里不再解码）

① 前置 kernel（每层跑一次，成本固定 ~0.5ms，和 token 数无关）：读 4 位权重和 s2、z，逐元素算 (w4−z)×s2，写出 8 位整数权重到临时缓冲区。这里用朴素乘法不心疼——该 kernel 是带宽瓶颈，算术单元大量空闲→ ② 主 kernel 的 TMA 直接搬 8 位权重行（每行 128 字节）进共享内存——解码工序、查表、同步栅栏整段消失→ ③ 大 tile（BLOCK_N=256）的 SS 形态 WGMMA；因为 s1 沿 K 恒定、token 缩放也沿 K 恒定，整条 K 的几十条指令一链到底，主循环里零次补缩放→ ④ 循环结束只补一次：token 缩放 × s1 × 整数转浮点
为什么大 token 数换这条路：swapAB 路径里同一份权重每 64 个 token 就要重新解码一遍（解码开销随 token 数线性涨）；预解码把它变成每层一次，token 再多也共享。反过来小 token 数绝不能走这条路——0.5ms 固定成本比整个 GEMM 还贵。

三、第一层（gate/up 投影）算完之后：融合出口（epilogue）

最终浮点累加器（gate 和 up 交织排列）→ 乘专家全局缩放（如有）→ gate 上限截断、up 双向截断 → SwiGLU：silu(gate)×up → 乘路由权重→ 每 (token, 64 个通道) 求最大绝对值 ÷127 = 中间激活缩放（为什么是 64：一个 CTA 的权重 tile 宽 128 行，swiglu 两两合并后只剩 64 个通道——出口只看得见自己这 64 个，这是 tile 几何定的，与指令无关；碰巧 64 也是精度甜点）→ 量化成 8 位整数（截到 ±126、把 −1 改写成 0——这些字节借住在 fp8 类型的缓冲区里，必须避开 fp8 的两个 NaN 位模式）→ 整数 tile 经 TMA 写中间激活池，缩放写缩放池

四、第二层（down 投影）与出口

GEMM 流程与第一层相同（同一套查表/预解码、同一套 s1/s2/z），唯一区别：输入的缩放是 per-(token, 64)，沿 K 每 64 个元素换一次"尺子"——所以累加器按 64 一段分两本账（不同尺子的裸乘积不能混账），每半段各补一次中间激活缩放；s1 照旧攒到最后乘→ 最终累加器 → 转 bf16→ 按 token 元数据经 NVLink 直接散射写回源卡的合并缓冲区 → 各卡把 topk 份专家贡献求和 → 输出 y

五、一张总账：每个量在哪一步被"乘回来"

量粒度处理位置为什么在那里
组缩放 s2（整数）每行 × 每 128 个 K解码时折进查表/预解码乘法（整数域，精确）整数可以无损吸收整数缩放
零点 z每行 × 每 128 个 K同上（−z×s2 折进表项）同上
行缩放 s1（bf16）每输出通道promote：整数累加完成后乘（沿 K 恒定→大 M 整条 K 只乘一次）任意浮点进不了整数值域，只能事后乘；恒定所以可无限推迟
token 缩放每 tokenpromote，同上它是激活量化的定义本身，唯一位置就是乘回累加器，任何方案都一样
中间激活缩放每 token × 每 64 通道第二层 promote，按 64 一段沿 K 会变，链到 64 就得结账
核心不变式：WGMMA 前后是一条"整数国境线"——所有能折进整数域的缩放（s2、z）在解码前搞定，所有必须是浮点的缩放（s1、token 缩放）在累加后搞定，中间的矩阵乘累加是纯整数、bit 精确、零舍入。
