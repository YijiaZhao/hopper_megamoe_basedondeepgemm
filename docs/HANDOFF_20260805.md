## 0. 三十秒版

在 DeepGEMM 底座上做的 **SM90 融合 MoE 内核**，把 dispatch + GG1 + SwiGLU + requant + GG2 + combine
压进 **2 个 kernel**，跨卡通信融合进计算。

- **8 卡 EP8：领先 FlashInfer + 2×allreduce 5~19%** ← 这是全部价值所在
- **单卡：落后 FlashInfer** ← 融合的代价，无通信可省时纯亏
- **价值来源**：把 28~36 us 的 dispatch/combine 通信藏进计算，对手只能串行做 2 次 allreduce

## 5. 为什么单卡慢：SMEM 预算

Hopper 每 SM 228 KB。MegaMoE 的固定开销 ≈ **60 KB**（纯 GEMM ≈ 8 KB）：

| 占用者 | 大小 | 为什么省不掉 |
|---|---|---|
| **epilogue 暂存 fp32** | **32 KB** | per-token 动态量化有「全行依赖」：算完整行才能求 amax |
| **epilogue 暂存 fp8** | **8 KB** | TMA 只能 shared→global，量化结果必须先落 SMEM |
| **跨卡搬 token** | **16 KB** | `kHidden × 4 个 dispatch warp`，TMA 无 global→global |
| expert 计数 + combine + barrier | ~4 KB | — |

每级 stage ≈ 25 KB ⇒ **只剩 3~4 级**（纯 GEMM 8 级）⇒ 藏不住 HBM ~600ns 延迟 ⇒
**latency-bound，DRAM 仅 26% roofline，单 GEMM 1 TB/s（FI 2.5 TB/s）**。

**大头是 epilogue 暂存（40 KB），不是通信（16 KB）** —— 即使不融合通信，SMEM 依然紧张。

**别人为什么不需要**：纯 GEMM 不量化；per-tensor 量化不依赖整行；拆两个 kernel 把依赖挪到外面（代价：多一次 launch + 多一遍显存往返）。

## 6. 量化方案

### 权重（离线 prepack，随 `l1/l2_weights` 走，**不在 sym_buffer**）
```python
# quantize_qoq()，ZP 分支
s1 = (w.abs().amax(dim=-1) / 120.0).to(bfloat16)   # per-row，bf16
w8 = (w / s1).round().clamp(-112, 112)
s2 = ceil((mx - mn) / 15.0).clamp(1, 127)          # per-K128，整数
z  = round(-mn / s2).clamp(0, 15)                  # per-K128，uint4
w4 = (w8g / s2 + z).round().clamp(0, 15)           # uint4
dec8 = (w4 - z) * s2 ;  dequant = dec8 * s1
```
三者打包进一个 **32-bit plane 字**：`[s1 bf16 16位 | z 8位 | s2 8位]`，
tile-major 重排成 **5 维 scale_meta** `[E, N/bn, Kb, bn, 4]`，并熔进 packed 权重。

**关键**：`s2` 组宽 128 **恰好等于 BLOCK_K** ⇒ 每 K128 只 promote 一次 ⇒ 比 mxfp4（每 K32 四次）快 8~13%。

### 激活（在 sym_buffer，跨卡）
| | int4 路 | mxfp4 路 |
|---|---|---|
| `buffer.x` | int8（`per_token_int8`，`.view(fp8)` 塞入） | fp8 e4m3 |
| `buffer.x_sf` 布局 | `[m, H/128]` | `[m, H/128]`（相同） |
| 数值粒度 | **per-token 整行一个**（amax/127），32 份为广播复制 | **per-token × K128 各一个**（amax/448） |

> 内核**支持真 per-K128**；int 路的参考量化器只算一个再广播 —— 若生产侧给真 per-K128，
> 内核直接能吃，**是免费的精度改进**。

## 8. 已否决的方案（别再试）

| 方案 | 否决原因 |
|---|---|
| **LiquidGEMM 式 IMAD 折 s2**（`(w·s2+a)^0x80`） | 真实数据最大字节顶到 **260 > 255** 溢出。我们 `clamp(±112)` 是为另一约束定的；要用得改量化方案，而收益天花板已知只有 1~2.5% |
| mxfp4 K128 probe | 数值无效（cosine ~0.74），仅作速度上限探针 |
| 单纯加深 prefetch | SMEM 不够，见第 5 节 |

## 9. 踩过的坑

1. **`scaled256` 只有调用没有定义**（提交 `2fd53b8` 遗漏）→ 编译失败**静默回退**到普通 REL_LUT →
   一度误判「scaled-MXFP4 收益很小」。**改完必须看编译是否真的走了新分支。**
2. **只同步部分文件**：从 .10 同步回本地时漏了 `mxfp4_dequant.cuh`，导致编译报 undefined。
   **用全量 md5 比对，别只比改过的那几个。**
3. **`#define` 与 format 参数必须严格同序**：host 侧 hpp 里加宏时，
   `#define DG_XXX {}` 的顺序必须和后面 format 参数列表**完全对应**，错位会让所有后续宏拿错值。
4. **第一轮 bench 含 JIT 编译污染**，必须多轮取中位数。
5. **KF 报的加速（5.68×）是相对 PyTorch 的独立微内核**，不是相对我们的内核。
   移植回 MegaMoE 的实际增益是 1.7~5.8%。**汇报时别混。**
